# iOS USB 相机批量删除设计

## 目标

在 App 内的 USB 相机相册中，允许用户选择一张或多张相机文件，并通过 iOS ImageCaptureCore 原生能力从相机存储卡删除。删除不影响已经保存到 iPhone 系统相册的副本。

本次只改 USB 相机删除。USB 后台下载与中断恢复属于独立生命周期改造，不纳入本次实现。

## 现状

- `WiredCameraImportService` 已使用 `ICCameraDevice.requestDeleteFiles`，但每次只传入一个 `ICCameraFile`。
- `WiredCameraDeletePolicy` 要求恰好选中一张未导入文件。
- 选中多张时，界面隐藏删除按钮。
- ImageCaptureCore 的批量删除接口接收 `[ICCameraItem]`，并分别返回成功和失败的文件集合。

## 交互设计

用户在 USB 相机相册中选择一张或多张文件后，底部操作栏显示删除按钮。删除范围包括当前实时目录中选中的可导入文件，不因文件已导入到手机而排除。

点击删除后显示不可逆确认框：

- 单张：显示文件名，并明确“只删除相机存储卡中的文件”。
- 多张：显示选中数量，以及其中已导入和未导入的数量。
- 确认按钮使用破坏性样式，取消不改变选择和相机内容。

删除期间禁用选择、导入、再次删除和预览操作。删除完成后保留未删除文件的选择，已经删除成功的文件从目录和选择中移除。

## 删除流程

1. UI 从实时相机目录解析选中的文件，拒绝缓存快照、空选择和操作进行中的请求。
2. Service 将所有有效 ID 一次映射成 `ICCameraFile` 数组。
3. Service 等待正在执行的缩略图请求结束，并暂停新的缩略图请求。
4. Service 对整个数组调用一次 `requestDeleteFiles(_:deleteFailed:completion:)`。
5. Service 根据 `result[.successful]` 和 `result[.failed]` 生成结构化结果，而不是只依据顶层 `error` 判断。
6. 完成后刷新相机目录，并恢复缩略图队列。
7. UI 显示全部成功、部分成功或全部失败的数量，并同步选择状态。

## 结果语义

新增批量删除结果，至少包含：

- 请求数量；
- 成功删除的 item ID；
- 明确失败的 item ID；
- 无法从返回结果确认的 item ID；
- ImageCaptureCore 返回的整体错误。

只有明确出现在成功集合中的文件才算删除成功。顶层 `error == nil` 但返回集合缺少某些文件时，这些文件标记为结果未知，不能宣称成功。

如果相机在完成回调前通过 `didRemove` 更新目录，最终仍以删除回调的结构化结果和刷新后的实时目录共同更新 UI。不会因为超时、部分失败或结果未知自动重试，以免第一次请求已在相机端生效。

## 能力与错误处理

- 相机会话未打开、文件已经不在实时目录或另一项前台相机操作正在进行时，拒绝请求并显示明确错误。
- 相机未声明单文件删除能力时仍允许调用系统批量 API，因为现有设备可能不完整报告 capability；同时保留 capability 日志供真机判断。
- USB 断开或会话关闭时结束本次操作，刷新为空目录，并报告未确认结果。
- iOS 上没有可用的 `cancelDelete`，因此 UI 不提供删除中取消。

## 测试

自动化测试覆盖：

- 单选和多选均可生成删除集合；
- 已导入文件仍可删除相机原件；
- 缓存目录、空选择、导入中和删除中被拒绝；
- 全部成功、部分成功、全部失败和结果缺失的映射；
- 成功项从选择中移除，失败和未知项仍保持可见、可选；
- 删除期间其他相机操作被阻止。

真机验收使用新拍、可丢弃的测试照片，分别验证单张、两张批量和一项失败场景。验收必须确认相机存储卡目录实际变化，并确认 iPhone 系统相册中的既有副本没有被删除。

## 非目标

- 不删除 iPhone 系统相册内容。
- 不实现 Wi-Fi/PTP 图库删除。
- 不实现后台删除、自动重试或删除撤销。
- 不在本次修改 USB 下载的后台生命周期和恢复机制。
